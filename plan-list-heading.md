You are working on an IELTS Reading mock test application.

## Context

The application has this structure:

- Admin creates an IELTS Reading test.
- Each test contains 3 passages.
- Each passage contains passage content and multiple questions.
- Admin clicks `Add Question` and selects a question type.
- The question form changes according to the selected question type.

We are currently designing the **Reading Passage structure** and the **List of Headings** question type.

The application uses **Supabase/PostgreSQL**.

---

# Core Requirement

A Reading passage must NOT require the admin to manually define paragraphs by default.

The admin should be able to enter the entire passage normally in a rich-text editor.

However, some IELTS Reading question types, especially **List of Headings**, require the system to know which parts of the passage are individual paragraphs.

Do NOT assume that every newline, blank line, or spacing in the editor represents a paragraph.

For IELTS content, visual line breaks do not always correspond to actual paragraph boundaries.

Therefore:

> Paragraph boundaries must be explicitly defined by the admin when a question type requires paragraph identification.

---

# Passage Editor

The default passage creation UI should be simple:

```text
PASSAGE 1

Title
[........................................]

Passage Content
┌─────────────────────────────────────────┐
│                                         │
│ Full passage content                    │
│                                         │
│                                         │
└─────────────────────────────────────────┘

[ + Add Question ]
```

Do NOT force the admin to enter:

- Paragraph 1
- Paragraph 2
- Paragraph 3
- Paragraph 4

when the passage does not require paragraph identification.

The passage should initially be stored as one complete piece of content.

---

# Paragraph Identification

Paragraph identification is an additional structure attached to a passage.

It should only be created when necessary.

For example, when the admin creates:

```text
Add Question
→ List of Headings
```

the application should recognize that this question requires paragraph identification.

Show an action such as:

```text
This question requires paragraph identification.

[ Define Paragraphs ]
```

The admin can then manually define paragraph boundaries.

---

# Important: Do NOT Auto-detect Paragraphs as Final Structure

Do not use:

- newline
- double newline
- HTML `<p>`
- spacing
- line breaks

as the authoritative paragraph boundary.

These may be used as a starting suggestion, but they must NOT automatically become the final IELTS paragraph structure.

The final paragraph structure must be controlled by the admin.

---

# Recommended Paragraph Editing UX

Use a manual segmentation workflow.

Example:

```text
DEFINE PARAGRAPHS

Agriculture has played an important role in human civilization.
Early farmers began to cultivate crops thousands of years ago.

────────────────── Split Here ──────────────────

Over time, agricultural techniques became increasingly sophisticated.
Farmers developed new methods to improve productivity.

────────────────── Split Here ──────────────────

Modern agriculture now relies heavily on technology.
```

The admin can click `Split Here` to create a paragraph boundary.

The resulting structure becomes:

```text
Paragraph 1
Agriculture has played...
Early farmers began...

Paragraph 2
Over time...
Farmers developed...

Paragraph 3
Modern agriculture...
```

The system should support:

- Add paragraph boundary
- Remove paragraph boundary
- Reorder only if technically necessary
- Edit paragraph content
- Preserve the original passage content

Do not make the admin manually type `A`, `B`, `C`, etc.

---

# Paragraph Identifiers

For List of Headings, the student-facing IELTS format may use:

```text
A
B
C
D
E
```

as paragraph identifiers.

However, internally paragraphs must have stable UUIDs.

Do NOT use `A`, `B`, `C` as database primary keys.

Recommended structure:

```text
paragraph UUID
paragraph_order
display_identifier
content
```

Example:

```json
{
  "id": "uuid-1",
  "paragraph_order": 1,
  "identifier": "A",
  "content": "..."
}
```

The identifier should be generated by the system according to paragraph order unless there is a strong reason to make it manually editable.

---

# Important Distinction

There are two different kinds of identifiers:

## Paragraph identifier

Example:

```text
A. Paragraph content...
B. Paragraph content...
C. Paragraph content...
```

## Heading identifier

Example:

```text
A. The history of the discovery
B. An unexpected problem
C. How the system works
D. Future developments
E. The first successful experiment
```

These are different entities.

Do not mix them.

Internally:

```text
paragraph.id = UUID
paragraph.identifier = A

heading.key = A
heading.text = "The history of the discovery"
```

A paragraph and a heading may both visually use `A`, but they must remain separate database entities.

---

# List of Headings Question UI

After paragraph structure has been defined, the question form should look approximately like:

```text
QUESTION TYPE
[ List of Headings ]

Instructions
[ Choose the correct heading for each paragraph. ]

HEADINGS

A  [ The history of the discovery        ]
B  [ An unexpected problem                ]
C  [ How the system works                 ]
D  [ Future developments                   ]
E  [ The first successful experiment      ]

[ + Add Heading ]


PARAGRAPHS TO MATCH

Paragraph A    [ B ▼ ]
Paragraph B    [ E ▼ ]
Paragraph C    [ A ▼ ]
Paragraph D    [ — ▼ ]

[ Save Question ]
```

The paragraph content itself should NOT be duplicated inside the question.

The question references the paragraph entities belonging to the passage.

---

# Database Design

Use relational tables for stable entities.

Do NOT put the entire test, passages, paragraphs, and questions into one giant JSONB document.

Recommended conceptual schema:

```text
tests
  id
  title
  ...

passages
  id
  test_id
  passage_number
  title
  content
  ...

passage_paragraphs
  id
  passage_id
  paragraph_order
  identifier
  content
  ...

questions
  id
  passage_id
  question_number
  question_type
  question_data JSONB
  ...
```

JSONB should be used for question-type-specific data.

For example, List of Headings can store:

```json
{
  "headings": [
    {
      "key": "A",
      "text": "The history of the discovery"
    },
    {
      "key": "B",
      "text": "An unexpected problem"
    },
    {
      "key": "C",
      "text": "How the system works"
    }
  ],
  "answers": [
    {
      "paragraph_id": "uuid-paragraph-1",
      "heading_key": "B"
    },
    {
      "paragraph_id": "uuid-paragraph-2",
      "heading_key": "A"
    }
  ]
}
```

The answer must reference `paragraph_id`, not `paragraph_number`.

This is important because paragraph order may change.

---

# Passage Content vs Paragraph Content

Avoid creating two completely independent sources of truth.

The original passage content must remain available.

When paragraph segmentation is enabled, the application needs a clear strategy for how paragraph content relates to the original passage.

Prefer an implementation that avoids silent data duplication or inconsistent passage/paragraph content.

If the current application architecture already has a rich-text document model, inspect it first and adapt the implementation rather than introducing an unnecessary second content system.

---

# General Architecture Principle

The system should behave like this:

```text
Create Passage
     │
     └── Full passage content
             │
             ├── Multiple Choice
             ├── True / False / Not Given
             ├── Fill in the Blank
             │
             └── List of Headings
                     │
                     └── Requires paragraph structure
                             │
                             └── Admin manually defines boundaries
```

Therefore:

- Normal passage → no paragraph segmentation required.
- List of Headings → paragraph segmentation required.
- Other question types → only require paragraph structure if their requirements actually need it.
- Never infer that every passage needs paragraph identifiers.
